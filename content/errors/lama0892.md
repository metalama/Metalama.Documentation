# LAMA0892: A static member of compile-time code must be durable

| | |
|---|---|
| **Severity** | Warning |
| **Reported by** | Metalama.Framework |
| **Message** | `'<Type>' is loaded in the compiler process, but its static member '<Member>' is of type '<MemberType>', which is not durable. A static field of a compile-time type is shared by every aspect instance, every target and every compilation, and at design time it keeps its value for as long as the analysis process runs. The member must therefore not reference a compilation, a syntax tree, a symbol or a code model declaration. If its value references none of these objects, mark the member or its type with [Durable]. Path: <Path>.` |

## Cause

Compile-time code, such as aspects, fabrics, and types marked <xref:Metalama.Framework.Aspects.CompileTimeAttribute?text=[CompileTime]> or <xref:Metalama.Framework.Aspects.RunTimeOrCompileTimeAttribute?text=[RunTimeOrCompileTime]>, is loaded in the compiler process. A static field of such a type keeps its value for as long as the assembly is loaded. At design time, that's as long as the IDE's analysis process runs, while Roslyn creates a new compilation on almost every keystroke. A static member that references a compilation, a syntax tree, a Roslyn symbol, or a code model declaration therefore keeps an old compilation, and every syntax tree of the project, in memory.

An immutable value can still hold such a reference: a symbol, a syntax node, a code model type, or a delegate can't change, but it keeps alive everything it references. That's why Metalama checks the static members of compile-time code for _durability_ in addition to immutability. A type is durable when it's safe to keep across compilations: intrinsic types such as `int` and `string`, immutable collections of durable types, <xref:Metalama.Framework.Code.IDurableRef>, and types marked with <xref:Metalama.Framework.Utilities.DurableAttribute?text=[Durable]>. Durability is opt-in: a type of your own isn't durable unless you mark it.

Metalama reports LAMA0892 on a static field or static automatic property of a compile-time or run-time-or-compile-time type when all of the following conditions hold:

* The member is read-only and its type is immutable. Otherwise, Metalama reports <xref:lama0889?text=LAMA0889>, <xref:lama0890?text=LAMA0890>, or <xref:lama0891?text=LAMA0891> instead, and only one of these diagnostics is reported for a member.
* The member type isn't durable, and the member itself isn't marked `[Durable]`.

Constants, templates, and introduced members aren't checked. In a run-time-or-compile-time type, a member marked <xref:Metalama.Framework.Aspects.RunTimeAttribute?text=[RunTime]> isn't checked either, because it doesn't exist in the compile-time assembly.

In the message, `<Type>` is the type that declares the member, `<Member>` is its name, and `<MemberType>` is its declared type. `<Path>` is the chain of members and types from `<Type>` to the type that isn't durable, followed by the reason in parentheses, for instance `the type is not marked [Durable]` or `a delegate holds its target and everything its closure captured`.

## Resolution

Choose the fix that matches what the member really holds:

* **The type holds only durable data.** If the type is yours, mark it with <xref:Metalama.Framework.Utilities.DurableAttribute?text=[Durable]>. The Metalama analyzer then verifies that its instance members are durable in turn. If you don't own the type, declare it durable with the `MetalamaDurableType` MSBuild item.
* **The member's declared type is broader than its value.** For a delegate that captures nothing, or a member typed as an interface or `object`, mark the member itself with `[Durable]`. This waives the check on the declared type, and the analyzer verifies instead that every value assigned to the member is durable.
* **The member references a compilation, a symbol, or a declaration.** Don't keep this object in a static member. Store a durable identifier instead, such as an <xref:Metalama.Framework.Code.IDurableRef>, and resolve it in the current compilation when you need it. Or compute the value in the aspect's `BuildAspect` method or in the template, where it's tied to the current compilation.
