# LAMA0288: A compile-time call with side effects can't depend on a run-time condition

| | |
|---|---|
| **Severity** | Error |
| **Reported by** | Metalama.Framework |
| **Message** | `The compile-time expression '<Expression>' cannot be used as a statement here because the statement is in a block whose execution depends on a run-time condition ('<RunTimeCondition>'). A compile-time expression used as a statement is assumed to have side effects, and these side effects cannot depend on a run-time condition. Move the statement out of this block, or make the condition compile-time.` |

## Cause

Metalama executes the compile-time parts of a template once, when it generates the code, but the run-time parts execute later, when the program runs. When a block depends on a run-time condition, such as an `if` statement whose condition is a run-time expression, Metalama doesn't know at compile time whether the block will execute. Compile-time code in that block must not change compile-time state, because that change would depend on a condition that's unknown at compile time.

Metalama reports LAMA0288 when a block that depends on a run-time condition contains a compile-time expression, used as a statement, that Metalama assumes to have side effects. Typically, it's a call to a method of a compile-time variable declared outside the block, or of a compile-time field or property, for instance `stringBuilder.Append( ", " )` or `list.Add( item )`. Calls on compile-time variables declared inside the block, auxiliary template calls, and methods like `meta.InsertStatement` aren't affected. The `<RunTimeCondition>` placeholder shows the run-time condition, or the construct that makes the block conditional, for instance `catch`, `finally`, or a local function.

A common cause is a variable that you intend to be compile-time but that Metalama infers to be run-time. ## Resolution

Depending on your intent, do one of the following:

* If the condition should be evaluated at compile time, make it compile-time, for instance by initializing the variables it uses with `meta.CompileTime`. The following example uses this approach.
* Move the compile-time statement out of the block.
* If the state is only needed inside the block, declare the compile-time variable inside the block.
